What Kind of System Is This?

Before looking at numbers, it helps to understand the system's design philosophy. Every architectural decision flows from one central choice made at the very beginning.

This is a multi-tenant SaaS platform built on top of PostgreSQL (via Supabase). The term "multi-tenant" means many independent healthcare organisations — clinics, hospitals, wellness centres — all run on the same software infrastructure, but with complete data isolation between them.

Think of it like a modern apartment building: every resident shares the plumbing and electricity, but no one can walk into another flat. The difference between a bad multi-tenant system and a good one is how deeply that isolation is enforced. Here it is enforced at the database layer itself, not just in application code.

This design means you can grow from 1 organisation to 500 without any architectural changes. The cost scales with usage, not with every new customer.

How Organisations Are Kept Separate

The single most important question for a healthcare platform is: can one clinic ever see another's patient data? The answer here is no — and it is enforced at the database level, not just in code.

Every row in every table carries an organisation_id stamp. The database is configured so that when a user from Clinic A sends a query, the database itself filters out everything that does not carry Clinic A's ID. Even if there were a bug in the application code, the database would return nothing.
Isolation Layer How It Works Status
organisation_id on every table Every record — patient, lead, task, invoice — belongs to exactly one org. All 25 tables follow this pattern. Active
Row Level Security (RLS) A PostgreSQL feature that attaches filtering rules to the database itself. Queries can only return rows the logged-in user is allowed to see. Needs tightening before launch
Organisation-scoped queries Every query function in the codebase explicitly filters by the current org's ID. Two layers of protection: application + database. Active
JWT authentication Every request carries a signed token that identifies the user and their org. Expired or tampered tokens are rejected before any query runs. Active
Note on RLS: RLS is enabled on all 25 tables. However, the current policies are intentionally wide-open for development (“allow all”). Before going live with real patient data, these must be switched to strict org-scoped policies. This is a known, defined task — estimated 2–3 days of engineering work.

How a Lead Becomes a Patient

One of the defining features of this platform is that a single person's journey from first enquiry to treated patient is tracked continuously, with no data loss between stages.

→
Lead

→

→
Appointment
Doctor + branch
→
Consultation

→
Invoice + Payment
Financial record
1Lead Created A lead carries personal details (name, phone, gender, source) plus pipeline metadata: stage, priority, assigned staff member, and custom fields. The enquiry source is always recorded so marketing attribution is available later.
2Follow-ups & Tasks Every call, WhatsApp message, email, and meeting is logged as a follow-up. Tasks keep staff accountable. Automation rules can trigger follow-up reminders automatically without anyone having to remember.
3Conversion When the lead agrees to treatment, a Patient record is created with a unique auto-generated patient code. The original lead is linked to the new patient via a foreign key — so the full enquiry history is never lost. Both records continue to exist and can be queried together.
4Consultation Each clinical visit creates a Consultation record: chief complaint, diagnosis, prescription, treatment plan, and structured vitals (blood pressure, weight, temperature, etc. stored as JSON). This is entirely separate from CRM or financial data — clean separation of concerns.
5Invoice & Payment Invoices link to both the patient and the specific appointment. Payments link to the invoice. This creates a clean financial chain: patient → appointment → invoice → payment. Every clinic's revenue is queryable independently, by branch or by doctor.

Infrastructure: Supabase Cloud vs. Self-Hosted

The platform currently runs on Supabase's managed cloud. At some point it makes sense to move to a self-hosted server. This section explains when that is and what it takes.

Supabase Cloud — Where We Are Now

  • Hosted and managed by Supabase Inc. (AWS infrastructure)
  • Free tier: 500 MB database, suitable for development and early pilots
  • They handle backups, upgrades, and infrastructure
  • Data sits on Supabase's servers outside India
  • Scales to Pro ($25/mo) when the free tier is outgrown
  • Fast to get started — no server management required
→

Self-Hosted — Where We Go Later

  • Your own VPS (Hostinger, AWS, or any cloud provider)
  • Full control: data never leaves your server
  • Meets data residency requirements (India, HIPAA, DPDP)
  • Same API as cloud — only 2 environment variables change
  • Scales to any size; no per-row fees
  • Requires basic server management capability
Migration is not a rewrite. Supabase is fully open source. Moving from cloud to self-hosted means running a database export (pg_dump), importing it to the new server, and changing two environment variables in the app. The application code does not change at all. Existing user accounts, passwords, and all data transfer perfectly.
QuestionAnswer
Will organisations lose any data during migration? No. pg_dump is a complete copy of every table, row, and relationship.
Will users need new passwords? No. Password hashes migrate with the auth schema. Users log in with the same credentials.
Will there be downtime? A short window (15–30 minutes) is required to do the export, import, and DNS switch. Best done off-hours.
Will the app behave differently after migration? No. The Supabase API is identical on cloud and self-hosted.
When should we migrate? When either: (a) the free tier storage runs out, (b) you need India data residency for compliance, or (c) you have enough organisations to justify the ~$9/mo VPS cost.

The platform is built on PostgreSQL, which has no meaningful upper limit. Instagram, Reddit, and Spotify all run on it. The bottlenecks that will appear with this system are known in advance and have defined solutions.

Pre-Launch Action Items

The platform is production-grade in its design and architecture. The items below are not architectural problems — they are defined engineering tasks that need to be completed before onboarding real patient data.

Tighten Row Level Security policies Priority 1

Change all 25 tables from “allow all” to strict org-scoped policies that enforce organization_id = current_user_org. This is the single most important task before any real patient data is stored. Estimated: 2–3 days.

Enforce role-based permissions in the UI Priority 2

The roles and permissions tables are fully built. The UI needs to read those permissions and show/hide features accordingly. Estimated: 3–5 days.

Move automation rules to server-side execution Priority 3

Currently rules run in the browser, which means they won’t fire for webhook-created leads or API integrations. Moving to Supabase Edge Functions ensures rules fire regardless of how a record is created.

Set up automated backups

On Supabase Cloud Pro, daily backups are included. On self-hosted, a daily pg_dump cron job needs to be configured and its output stored off-server (e.g. S3-compatible storage).

Full audit logging

Already implemented. All major actions are logged with who, what, when, and from where — including IP address and geolocation.

Organisation data isolation

Already implemented. Every table has organization_id; all queries are org-scoped at the application layer.
